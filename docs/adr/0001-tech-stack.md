# ADR-0001: 技術スタックの選定

- 日付: 2026-10-22
- ステータス: 提案

## 背景

- 小規模(当面は数十〜数千アクセス)だが、ECとして一通りの機能が必要。
- 最大の課題は「認知」。検索エンジンに載りやすいことが重要。
- 立ち上げ後はチーム開発に移行し、非エンジニアのメンバーも増える。
- 設計判断を、後から説明できる形で残すことも目的の一つ。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| ASP(BASE/STORES/Shopify等) | すぐ始められる。保守が軽い | 独自の業務フロー・将来のマルチ生産者に弱い。Shopifyの基本プランは複数の売り手に標準対応しない(サードパーティアプリが必要) |
| WordPress + WooCommerce | 低コストで構築できる。プラグインが豊富 | プラグイン依存で保守・脆弱性対応が必要。独自拡張で制約にぶつかりやすい |
| EC-CUBE等オープンソース | 国内実績が多い | 初期費用が大きくなりやすい(外注の場合の目安は50万〜200万円)。PHP中心の保守 |
| **Next.js + Supabase + Stripe(+ホスティング)** | SEOに強い。権限をDBで制御できる。マルチ生産者設計と相性が良い | 自前実装が多い。保守は開発者が担う |
| マイクロサービス(Amazon/ZOZO型) | 巨大規模・多人数並行開発に有効 | 小規模では運用コストだけが増える |

## 決定(提案)

**Next.js(App Router)+ TypeScript、Supabase(PostgreSQL・認証・RLS)、Stripe(決済)** を採用する。
ホスティングは `adr/0002` で別途決める。

理由:
1. **SEO**: 商品・物語ページをサーバー側で生成でき、認知不足という課題に効く。
2. **権限をDBで保証**: Supabaseの行レベルセキュリティで「生産者は自分のデータだけ」を構造的に保証でき、マルチ生産者化の核心を満たす。
3. **決済**: Stripeはカード・コンビニ払い・定期課金(応援会員)に対応でき、将来の売上分配(Stripe Connect)にも拡張できる。
4. **規模に見合う**: 1つのアプリを機能別に整理する**モジュラーモノリス**とし、将来分割できる境界(商品・注文・会員・生産者)だけを引く。

## 決定の前提(2026-10-23 追記)

- 自作を採る理由は、**独自の業務フロー**(応援会員、複数の生産者の参加、権限の分離)を、無理なく実現するためである。
- ASP(Shopify等)で足りる要件の間は、ASPの方が、保守の負担と引き渡し後のリスクは小さい。この点を踏まえたうえで、自作を採る。
- そのため、次を**必ず設計書に含める**。
  1. 引き渡し後の保守体制(担当者、連絡先、障害時の対応)
  2. 非エンジニアが更新できる管理画面と、操作手順書
  3. 運用費用がもっとも小さくなるホスティングの比較(adr/0002)
  4. 運営者が自作の運用を続けられなくなった場合に、ASPへ移行できる手順(商品・顧客データの書き出し)
- この方針の理由とリスクは、主催者に説明し、同意を得る。

## 採らなかったもの

- マイクロサービス: 数百人規模の並行開発とセール時の負荷に対する解であり、この規模では逆効果。
- WordPress: 「村の他の生産者が自分で出品する」段階でプラグインの制約を受けやすい。ただし、**短期間・低コストで事業を始める**ことが最優先になった場合は、有力な代替案として再検討する。

## 更新が必要な運用

- 非エンジニアが更新するお知らせ・成長日記・商品は、管理画面から編集できるようにする(F-06, F-14)。
- 決済プラグイン等への依存は持たない。決済はStripeの公式機能を用いる。

## 影響とリスク

- 自前実装のため、保守は継続的に必要。引き渡し後の保守担当を決める必要がある(要件定義書 NF-14)。
- 将来、要件が単純なままなら、ASPへの切り替えも選択肢として残す。

## 参考にした情報

- ZOZOTOWNはオンプレミスのモノリスからクラウド・マイクロサービスへ段階的に移行中(自社の求人・登壇資料)。
- Amazonは数百の疎結合サービスで構成される(公開された解説)。内部の詳細は非公開。
- マルチベンダーは、WooCommerceのプラグインやShopifyのアプリ、Stripe Connectで実現される例がある。
