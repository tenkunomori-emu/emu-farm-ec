# ADR-0009: 生産者のアカウントはダッシュボードなしのまま進め、登録は埋め込みの部品で行う

- 日付: 2026-11-21
- ステータス: 採用

## 背景

- ADR-0005([0005-stripe-account-holds-and-refunds.md](0005-stripe-account-holds-and-refunds.md))で、生産者の Stripe のアカウントを、ダッシュボードなし、Stripe の手数料は生産者、マイナス残高の責任は Stripe、情報の収集は Stripe の設定にし、登録は Stripe が用意する入力画面へのリンクで行うと決めた。
- ADR-0005 には、確かめていない点が残っていた。設定は Accounts v1 の項目で書かれている。ダッシュボードの選択肢に Express を挙げているが、Express と比べた記録がない。入力画面へのリンクをサーバーから API で作る方法と、不審請求は、テストしていない。
- Stripe のサンドボックスでは、Accounts v1 で生産者のアカウントを作れなかった(ADR-0008([0008-jcb-acceptance.md](0008-jcb-acceptance.md))の「影響とリスク」)。
- 基本設計の状態遷移と、決済と送金の流れは、Stripe の動きを前提にする。前提が違えば、手数料と損失をだれが負うかが変わる。そのため、これらを書く前に、Stripe のサンドボックスで、方式検証のコード([spikes/stripe/](../../spikes/stripe/))を動かして確かめた(2026年11月21日)。使った API の版は 2026-11-18.endive(正式な版)、stripe のライブラリは 23.2.0 である。確かめた記録は、議事録と同じく、このリポジトリの外に置いている。

## 検討した選択肢

### 生産者に渡す Stripe の画面(ダッシュボード)

| 選択肢 | Stripe の手数料は生産者、マイナス残高の責任は Stripe にできるか | 生産者の操作 | 判断 |
|---|---|---|---|
| Express のダッシュボード | 正式な版の API では、できない。Express では、手数料もマイナス残高の責任も、管理者の側にする組み合わせしか作れない。できる組み合わせは、2026年6月24日に公開プレビューとして出たものである | Stripe の Express の画面にログインして使う。マイナス残高の責任を Stripe にすると、Express の画面の「支払いを見る」「返金する」「不審請求に対応する」「残高に入金する」の機能は、無効にできない | 採らない。プレビューの機能は変わることがあり、お金の流れの土台に使わない |
| フルのダッシュボード | できる(フルでは、手数料もマイナス残高の責任も Stripe の側にする決まり) | メールアドレス、パスワード、2段階認証を持つ Stripe のアカウントで、Stripe の画面にログインして使う。Stripe の画面で、代金の確定、取り消し、返金を行える | 採らない。代金の確定、取り消し、返金がサイトの外で起きると、返金は1つの注文に1回の決まり(要件定義書([01-requirements.md](../01-requirements.md))の FR-087)、返金の内訳、返金の申し出の流れが崩れ、購入者が見る注文の画面とお金がずれる |
| **ダッシュボードなし** | できる(サンドボックスで、正式な版の API で作れた) | サイトの中に組み込んだ Stripe の画面部品を使う。部品を使うときに、電話番号と SMS の確認コードによる Stripe のログインを行う | **採用**。代金の確定、取り消し、返金が、サイトの操作だけで起きる。生産者は、Stripe のパスワードを持たない |

### 生産者の登録の方法

| 選択肢 | 確かめた結果 | 判断 |
|---|---|---|
| Stripe が用意する入力画面へのリンク(Account Link) | サンドボックスでは、API でリンクを作れ(期限は作ってから5分)、入力を終えると、カード決済と入金が有効になった。ただし、Stripe の公式ページは、ダッシュボードがなくマイナス残高の責任が Stripe のアカウントでの扱いが、ページによって違う。「Create connected accounts with Managed Risk」は、入力画面でも埋め込みの登録でもよいとしている。「Embedded Managed Risk」と「Fully embedded Connect platform integration」は、組み込みを求める部品に、登録の部品を挙げている。「Stripe-hosted onboarding」には、この設定のアカウントは埋め込みの部品を使う必要がある、という文がある | 採らない。サンドボックスは、本番で使えない操作を通すことがあり、本番で通る保証がない。本番で初めて登録できないと分かると、生産者の登録が止まる |
| **埋め込みの登録の部品(Account onboarding)** | サンドボックスで、日本の生産者のアカウントで読み込め、入力を終えると、カード決済と入金が有効になった | **採用**。上のどの公式ページとも食い違わない。5分で切れるリンクを作り直す流れが要らない |

### 不審請求の証拠を出す手段

| 選択肢 | 確かめた結果 | 判断 |
|---|---|---|
| 埋め込みの画面部品(Disputes for a payment) | 返金の操作を見せずに使え、証拠を出す期限と不審請求の手数料を表示し、証拠を出せた。ただし、部品を使う許可(AccountSession)は、生産者のアカウントの全体に出て、1件の支払いに絞れない。同じ許可で、別の支払いの不審請求も表示された | ログインした生産者の画面(FR-098)で使う |
| API | サーバーが、指定した1件の不審請求だけを扱える。Stripe は、不審請求への対応を API で作ってもよいとしている(「Embedded Managed Risk」) | 生産者の役割が外れた生産者が、ログインせずに開く証拠のページ(FR-238、FR-239)で使う。メールのリンクを知った人が、同じ生産者のほかの不審請求を開けないようにするためである |

## 決定

### 1. 生産者のアカウントの設定

- 生産者のアカウントは、Accounts v2 で、ダッシュボードなし(dashboard: none)、Stripe の手数料は生産者(fees_collector: stripe)、マイナス残高の責任は Stripe(losses_collector: stripe)の設定で作る(FR-007、FR-008、FR-009)。ADR-0005 の「1. 生産者のアカウントの設定」の設定の中身は、変えない。
- 情報の収集は、Accounts v2 では選ぶ設定ではなく、上の設定から Stripe に決まる値である(requirements_collector: stripe)。ADR-0005 は、選ぶ設定として書いている。

### 2. 生産者の登録

- 生産者は、本人確認と銀行口座の情報を、サイトのページに組み込んだ、Stripe の埋め込みの登録の部品で入力する。ADR-0005 の「入力画面へのリンクは、サイトにログインした生産者に、その場で作って渡す」は、この決定に置き換わる。
- 入力が終わったかを、サイトが Stripe からアカウントの状態を取得して判断することは、ADR-0005 のまま変えない。

### 3. サイトに組み込む部品

- 登録、アカウントの管理、お知らせのバナーを組み込む。ダッシュボードを渡さずに、マイナス残高の責任を Stripe にするときの、Stripe の条件のためである。
- 書類を組み込む。Stripe の手数料を Stripe が生産者から直接受け取る場合に、必要な部品に挙がっているためである。
- 売上と入金の確かめ(FR-207)は、残高の部品を使う見込みとする。部品と API の使い分けは、基本設計の外部連携で決める。
- 生産者が自分の残高にお金を足す手段は、MVP では作らない。Stripe は、これを必須とせず、勧めるとしている。

### 4. 生産者の Stripe のログイン

- 登録の部品とアカウントの管理の部品は、生産者に、Stripe のログインを求める。ログインは、部品から開く Stripe の窓で、電話番号と、SMS で届く確認コードを入れる形で、パスワードは作らない。情報の収集を Stripe が受け持つ設定では、このログインを止められない。
- 生産者が Stripe のダッシュボードを使わないこと(FR-007)は、変わらない。

### 5. 不審請求の証拠を出す手段

- ログインした生産者の画面(FR-098)では、埋め込みの画面部品(Disputes for a payment)を、返金の操作を無効にして使う。
- 生産者の役割が外れた生産者の証拠のページ(FR-238、FR-239)では、部品を使わず、サーバーがその1件の不審請求だけを API で扱う。

## 確認できた事実(サンドボックスと公式ページ、2026-11-21時点)

テストは、日本の個人のテスト用アカウントで行った。支払いは、3,000円(アプリケーション手数料450円)を、仮押さえしてから確定した。

| 確かめたこと | 結果 |
|---|---|
| 「1. 生産者のアカウントの設定」のアカウントを、Accounts v2 の正式な版で作る | 作れた。Stripe が返した値は、dashboard が none、fees_collector、losses_collector、requirements_collector がどれも stripe。作った直後に足りない27の項目は、どれも生産者本人の入力を待つもので、管理者が代わりに入れる項目はなかった |
| 埋め込みの登録の部品 | 日本のアカウントで読み込めた。最初に、Stripe の窓で、電話番号と SMS の確認コードによるログインを求められた。そのあとの入力(氏名、住所、銀行口座、写真付きの身分証明書による本人確認)は、サイトのページの中の部品で進んだ。入力を終えると、カード決済と入金が有効になり、足りない項目は0になった |
| 入力画面へのリンク(Account Link)を API で作る | 作れた。期限は作ってから5分。入力を終えると、カード決済と入金が有効になった。求められた項目は、漢字とカタカナの氏名と住所、業種、ウェブサイト、商品の説明、割賦販売法に関する質問、銀行口座、写真付きの身分証明書による本人確認 |
| アカウントの管理、お知らせのバナー、残高、書類の部品 | 4つとも、日本のアカウントで読み込めた。アカウントの管理は、情報を見るときにも直すときにも、Stripe のログインを求めた。同じブラウザーでは、ページを開き直しても、もう一度は求められなかった。お知らせのバナーは、求められている情報がないため、何も表示しなかった。残高の部品には、残高が0円のとき、残高にお金を足す操作は表示されなかった |
| すぐに使える残高が0円のときの、全額の返金 | すぐに成功し、生産者の残高が -569円になった(受け取った2,431円より多い3,000円を返したため)。ADR-0005 の記録と同じ動きである |
| 支払いの受け付けが無効の間の、代金の確定と返金 | 確かめられなかった。このアカウントの設定では、サンドボックスで、有効になった受け付けを、あとから無効に戻す方法がない |
| 不審請求 | 不審請求の額3,000円と、不審請求の手数料1,650円が、生産者の残高から引かれた。不審請求が開いている間、その支払いは返金できなかった。勝つと、額の3,000円だけが戻り、手数料は戻らなかった。勝ったあと、その支払いは、返金できる状態に戻った |
| 照会(不審請求の前に、カード会社が説明を求める段階) | 日本のアカウントで起こせた。お金は引かれず、その支払いは返金できた。証拠を出すと、不審請求に進まずに閉じた |
| 証拠を出す期限 | 不審請求と照会ごとに、Stripe が示した(FR-266) |
| 不審請求の部品(Disputes for a payment) | 返金の操作を見せずに使え、証拠を出す期限と不審請求の手数料を表示し、証拠を出せた。争わずに負けを認める操作(不審請求の申請を承諾)も表示された。部品を使う許可は、1件の支払いに絞れなかった |
| 購入手続きの画面(Checkout)で、カードのブランドを止める指定(brands_blocked に discover_global_network) | JCB とダイナースクラブのテスト用のカードは、支払いの前に止まり、Visa は支払えた。ディスカバーのテスト用のカードは、試していない |
| Stripe の領収書の、税率ごとの消費税 | 行ごとに税込みの税率(商品は8%、送料は10%)を付けると、購入手続きの画面と領収書に、税率ごとの消費税が別の行で出た。領収書の発行者は生産者で、問い合わせ先は、生産者が登録した電話番号だった。領収書の見出しは英語で、適格請求書の登録番号は出なかった |

公式ページで確かめたこと:

- Accounts v2 の組み合わせの制約は、マイナス残高の責任を管理者にするなら手数料も管理者、Express なら両方とも管理者、フルなら両方とも Stripe、の3つである。ダッシュボードなしで両方とも Stripe にすることを禁じる制約はない。
- Express で、手数料もマイナス残高の責任も Stripe の側にする組み合わせは、公開プレビューである。
- カードの返金は、すぐに使える残高が足りないと、足りるまで結果待ちになり、45日たっても足りなければ失敗する。
- 止めるブランドの値 discover_global_network には、ディスカバー、ダイナースクラブ、JCB のほかに、銀聯(UnionPay)と Elo が入っている。

## 影響とリスク

- サンドボックスの動きが、本番と同じとは限らない(ADR-0005 の「影響とリスク」)。次の点は、本番で確かめる。
  - 残高が足りないときの返金が、すぐに成功するか、結果待ちになるか。サンドボックスではすぐに成功したが、公式ページは結果待ちになるとしている。返金した注文の扱い(FR-087)と、失敗に変わった返金の扱い(FR-088)は、どちらの動きにも対応している。
  - 支払いの受け付けが無効の間の、代金の確定と返金。FR-011 は、Stripe がどちらに動いても結果が決まる形にしてあり、実装では、確定の失敗と返金の失敗をテストで確かめる。
  - 部品のログインに、メールアドレスも求められるか。ログインが続く期間。
  - 日本のカード会社が、照会を使うか。
- 登録の方法についての公式ページの食い違いのうち、「Stripe-hosted onboarding」は、Accounts v2 の版のページの全文を開けず、文の前後を確かめていない。
- 管理者のアカウントの残高は、読んでいない。返金と不審請求のお金が管理者から出ないことは、生産者の残高の増減が、返金の額、不審請求の額、不審請求の手数料と一致したことから判断した。
- 生産者は、登録のときに、写真付きの身分証明書、スマートフォン、銀行口座を用意する必要がある。生産者向けの案内に入れる。登録の項目のウェブサイトに、サイトが生産者の店のページの URL を前もって入れるかは、基本設計の外部連携で決める。
- 不審請求の部品には、争わずに負けを認める操作がある。生産者がこの操作をしても、結果は Stripe の知らせで受けるため、不審請求で負けたときと同じに扱える(FR-099、FR-265、FR-267)。
- 不審請求の証拠の画面は、購入者の氏名、メールアドレス、住所を、生産者に入力させる。生産者は、購入者のメールアドレスを知らない。サイトが持つ注文の記録を、証拠に前もって入れるかは、基本設計の外部連携で決める。カード会社が有力な証拠として挙げる運送会社と追跡番号は、今の要件では記録していない。
- 勝った不審請求の支払いは、返金できる状態に戻る。勝ったあとの返金の扱いは、基本設計の状態遷移で決める。
- カードのブランドを止める指定は、購入手続きの画面(Checkout)で確かめた。購入手続きをサイトに組み込む場合(Payment Element)の指定は、確かめていない。どちらを使うかと、組み込む場合の止め方は、基本設計の外部連携で決める(ADR-0008 の決定の3)。この指定では、銀聯と Elo も止まるが、受け付けるカードは Visa、Mastercard、American Express のため、影響はない。
- Stripe の領収書には、適格請求書の登録番号が出ない。今の要件(FR-067、FR-068)は、税率ごとの消費税を求めており、登録番号は求めていない。
- Express の組み合わせが正式な版になっても、マイナス残高の責任を Stripe にする限り、Express の画面の返金と不審請求の機能は無効にできない。生産者が Stripe の画面で返金できる点は残る。
