# ADR-0005: Stripe の生産者のアカウントの設定と、仮押さえ・返金の方式

- 日付: 2026-11-04
- ステータス: 採用

## 背景

- ADR-0004([0004-stripe-connect-direct-charges.md](0004-stripe-connect-direct-charges.md))で、支払いを Stripe Connect のダイレクト支払いにすると決めた。代金は生産者のアカウントに直接入り、管理者は代金を預からない。
- 要件定義書 v1.5([01-requirements.md](../01-requirements.md))では、注文のときに代金を仮押さえし、生産者が「発送する」を押したときに確定する(F-10、F-12)。決済のたびに、管理者がアプリケーション手数料を受け取る(F-31)。生産者は Stripe のダッシュボードを使わない(F-31)。
- お金の流れで、管理者が損をしない構成にする必要がある。返金や不審請求で、誰のお金が、どこから出るかを、設計の前に確かめる必要があった。
- そのため、Stripe のテスト環境(サンドボックス)で、日本の生産者のテスト用アカウントを作り、支払い、仮押さえ、確定、返金を実際に行って確かめた(2026年11月3日、4日)。テストの記録は、議事録と同じく、このリポジトリの外に置いている。

## 検討した選択肢

### 生産者のアカウントの設定

| 項目 | 選択肢 | 判断 |
|---|---|---|
| ダッシュボード | Stripe / Express / なし | **なし**。Stripe を選ぶと、生産者が情報を入力するリンクを開くのに、生産者自身の Stripe へのサインインが必要だった(テストで確認)。なしでは、サインインなしで入力画面が開いた |
| Stripe の手数料を払う人 | 生産者 / 管理者 | **生産者**。要件(F-31)のとおり |
| マイナス残高の責任 | Stripe / 管理者 | **Stripe**。管理者が、生産者の払えない分を負担しないため |
| 情報の収集(本人確認など) | Stripe / 管理者 | **Stripe**。管理者が集める形は、上の2つ(手数料は生産者、マイナス残高は Stripe)と一緒に使えない(Stripe の公式ドキュメント) |

### 代金の確定の時期

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 注文のときに確定する | 仕組みが単純 | 発送前のキャンセルや売り切れでも、返金になる。返金しても Stripe の手数料は戻らないため、生産者か購入者が手数料を損する |
| **注文のときに仮押さえし、発送のときに確定する** | 発送前のキャンセルは、仮押さえの取り消しで済み、手数料がかからない | 仮押さえには期限があり、期限までに発送しないと取り消される |

### 決済手段の決め方

| 選択肢 | 判断 |
|---|---|
| 支払いを作るときに、決済手段の種類を指定する(payment_method_types) | 使えない。このアカウントでは、指定するとエラーになる(テストで確認) |
| 支払いを作るときに、使ってよい決済手段を絞る(allowed_payment_method_types) | カードだけに絞れることは確かめた。カード以外(Link、Apple Pay、Google Pay)を含めたときの動きは、確かめていない |
| **Stripe の「決済手段の設定」で決める** | 採用。管理者の設定で、生産者ごとに使える決済手段が決まる。テストで、設定の変更が支払いに反映されることを確かめた |

## 決定

### 1. 生産者のアカウントの設定

- 生産者のアカウントは、ダッシュボードなし、Stripe の手数料は生産者、マイナス残高の責任は Stripe、情報の収集は Stripe、の設定で作る。
- 生産者は、本人確認と銀行口座の情報を、Stripe が用意する入力画面で入力する。入力画面へのリンクは、サイトにログインした生産者に、その場で作って渡す。リンクは1回だけ使え、数分で期限が切れるため、メールでは送らない。
- 登録したあとに、生産者が情報を直したり、Stripe からのお知らせや書類を見たりする画面は、Stripe の埋め込みの画面部品をサイトに組み込んで作る(ダッシュボードがないため)。
- 入力が終わったかは、サイトが Stripe からアカウントの状態を取得して判断し、足りない項目があれば生産者に知らせる。

### 2. 仮押さえと、発送のときの確定

- 購入者が注文すると、カードの代金を仮押さえする(この時点では、購入者に請求されていない)。支払いは、生産者のアカウントの上に作る。
- 生産者が「発送する」を押すと、サイトが代金を確定する。確定に成功したときだけ、生産者は荷物を渡す。
- 仮押さえの期限は、支払いごとに Stripe が示す期限(capture_before)を注文に保存して使う。日数をプログラムに書かない。期限はカードの種類で変わるため(日本の円の Visa、Mastercard、JCB などは最大30日、American Express は7日)。
- 期限が近づいたら、生産者に発送のお知らせを出す。期限までに確定されない注文は、サイトが自動で仮押さえを取り消し、在庫を戻し、生産者と購入者に知らせる。
- 発送前のキャンセルと、生産者が発送できないとき(売り切れなど)は、仮押さえを取り消す。購入者には請求されず、生産者にも管理者にも手数料はかからない。

### 3. アプリケーション手数料

- ADR-0004 の「販売手数料」は、アプリケーション手数料と呼ぶ(議事録_2026_1102)。率は、要件定義書 v1.5([01-requirements.md](../01-requirements.md))の F-31 で決めている(基本は15%、生産者ごとに設定で変えられる)。ADR-0004 の「率は、引き渡しの後に決める」は、この決定に置き換わる。
- アプリケーション手数料は、支払いを作るときに額を付ける。管理者が受け取るのは、代金を確定したときで、仮押さえの間は受け取らない。確定しないまま取り消した注文では、受け取らない。
- 額は、生産者ごとの率で、サイトが計算する(F-31)。確定したときに、Stripe の記録から、Stripe の手数料、その消費税、アプリケーション手数料の実際の額を読み、注文に保存する。
- 返金するときは、アプリケーション手数料の返金を指示しない。指示しなければ、全額返金でも一部返金でも、アプリケーション手数料は管理者に残る。

### 4. 返金と、生産者の残高がマイナスになる場合

- 返金のお金は、生産者の Stripe の残高から出る。管理者の残高からは出ない。
- 返金しても、Stripe の手数料(処理手数料と、その消費税)は戻らない。
- 購入者の都合の返金では、支払った額から、Stripe の手数料(実際の額)、アプリケーション手数料、送料(発送済みの場合)を引いた額を返す(F-16)。生産者の手元に残る額は0円になり、生産者は損も得もしない。手数料と送料は、購入者が負担する。
- 生産者の都合の返金では、生産者が決めた額を返す。Stripe の手数料とアプリケーション手数料は戻らないため、その分は生産者が負担する。
- 生産者の残高が足りなくても、返金は止まらず、生産者の残高がマイナスになる。マイナスの分は、その生産者のその後の売上から差し引かれる。生産者から回収できなかった分は Stripe が負担し、管理者は負担しない(1の設定で、マイナス残高の責任を Stripe にしているため)。日本の生産者の銀行口座からは、自動では引き落とされない。

### 5. 決済手段の設定

- 使える決済手段は、Stripe の「決済手段の設定」で決める。設定は、全体の設定(すべての生産者の初めの値)と、生産者ごとの設定の2段になっている。
- 全体の設定は、Stripe の API では変えられず、管理者が Stripe のダッシュボードで変える。テスト環境の設定は本番に引き継がれないため、本番の Stripe のアカウントでも、同じ設定を行う。手順は、操作手順書に書く。
- 全体の設定では、カード、Apple Pay、Google Pay、Link を有効にし、カードの分割払いを無効にする。PayPay とコンビニ払いは無効にする(要件定義書 v1.5([01-requirements.md](../01-requirements.md))の F-10)。
- JCB は、全体の設定では選べず、生産者ごとの設定になる。サイトの管理画面から、管理者が API で、生産者ごとに有効にする。JCB の審査が終わるまで、その生産者は JCB を使えないが、ほかのカード(Visa、Mastercard、American Express)は使える。
- 支払いを作るときに、payment_method_types は使わない。

## 確認できた事実(テスト環境と公式ドキュメント、2026-11-04時点)

テストは、日本の個人のテスト用アカウントで、1,000円の支払いと、アプリケーション手数料150円(15%)で行った。

| 確かめたこと | 結果 |
|---|---|
| 1の設定でアカウントを作り、入力を終えられるか | 作れた。カード払いと入金が有効になった |
| 仮押さえとアプリケーション手数料を付けた支払い | 作れた。状態は確定待ち。米国発行の Visa と日本発行の JCB のテストカードで、期限はどちらも作った時刻のちょうど30日後 |
| 確定したときの手数料の内訳 | Stripe の手数料36円、消費税4円、アプリケーション手数料150円。生産者の受け取りは810円。Visa と JCB で同じ |
| 仮押さえの間のアプリケーション手数料 | 記録はなく、確定したときに作られた |
| 一部返金(810円) | Stripe の手数料もアプリケーション手数料も戻らなかった。生産者の受け取りは、差し引き0円 |
| 全額返金(1,000円を2件) | 2件とも返金できた。生産者が受け取った額(1件810円)より多く返したため、生産者の残高は合計 -380円になった(1件あたり、Stripe の手数料40円とアプリケーション手数料150円の分)。アプリケーション手数料は戻らなかった |
| 仮押さえの取り消し | 生産者の残高は変わらず、アプリケーション手数料の記録も作られなかった |
| 支払いを作るときに payment_method_types を指定 | エラーになった |
| 管理者が API で、生産者ごとの設定の JCB を有効にする | 有効になった |

公式ドキュメントで確かめたこと:

- 日本のアカウントの円の取引では、Visa、Mastercard、JCB、Diners Club、Discover の仮押さえを、最大30日保てる。American Express と円以外の取引は、通常7日。
- 期限までに確定しないと、仮押さえは解かれ、支払いは取り消しになる。確定は、原則1回だけ。一部だけ確定すると、残りは解かれる。
- 返金しても、元の支払いの Stripe の手数料は戻らない。
- マイナス残高の責任を Stripe にしたアカウントでは、回収できない損失を Stripe が負う。マイナスの分は、その後の売上で相殺される。
- 銀行口座からのマイナス残高の自動の引き落としの対象国に、日本は入っていない。
- 日本の生産者のアカウントで JCB を使うには、JCB の審査がある。審査が終わるまで、新しい JCB の支払いは止まる。
- PayPay は、手動の確定(仮押さえ)に対応していない。

## 影響とリスク

- テスト環境では、使えない機能でも操作できる場合がある(Stripe の公式ドキュメント)。本番で同じ動きになるかは、本番で確かめる。
- 本番で JCB の審査が通るかは、確かめていない。Stripe の公式ドキュメントには、Stripe の手数料を生産者が払う設定では、管理者が生産者を JCB に登録できない、という記述がある。テスト環境では、管理者が API で有効にできたが、本番で同じになるかは分からない。
- 生産者の入力画面へのリンクを、サーバーから API で作る方法は、テストしていない(テストでは、ダッシュボードで作ったリンクを使った)。
- 不審請求(チャージバック)は、テストしていない。生産者の残高から引かれ、マイナスになる場合がある。
- 管理者のアカウントの残高は、テストで読んでいない。管理者が負担しないことは、テストの結果と公式ドキュメントから判断した。
- 日本の生産者の銀行口座から自動で引き落とされないため、売上のない生産者のマイナス残高は、回収されないまま残る場合がある。マイナスの間は、その生産者への入金が止まる。この場合も、損失は Stripe が負い、管理者は負担しない。管理者は、Stripe で生産者の入金を止めたり、残高から引き落としたりはできないため、問題のある生産者には、サイトで商品を非表示にする、販売を止める、などで対応する(議事録_2026_1102)。
- American Express の支払いは、注文から7日以内に発送する必要がある(F-12、F-14)。日本以外で発行された Visa は、Visa の規則で、10日を超えて確定も取り消しもしないと、手数料の対象になる(今の料金体系では Stripe が負担するが、将来は変わる可能性があると Stripe は書いている)。
- 複数の生産者の商品を1回の購入で買う場合の支払いは、決めていない(1回の支払いの代金は1人の生産者に入るため)。最初の生産者は1件なので、基本設計書 v0.1([03-basic-design.md](../03-basic-design.md))の第9章(未決事項)に、Issue #54 で加える。
