# ADR-0014: 結合テストは Stripe のサンドボックスにつなぎ、知らせはテストが署名して送り、期限は記録した日時を過去にして確かめる

- 日付: 2026-11-24
- ステータス: 採用

## 背景

- 開発の進め方([CONTRIBUTING.md](../../CONTRIBUTING.md#工程とゲート))の「工程とゲート」は、基本設計のゲートに、結合テストの方針があることを求めている。
- 詳細設計は、詳細設計書を作らず、機能ごとのマイグレーション、型、テストで書く(同じ節)。テストの道具と、外部のサービスへのつなぎ方が決まっていないと、最初の機能の PR で、テストを書けない。
- 開発の進め方の「重大な不具合」のうち、Stripe とデータベースの状態の食い違いと、二重の確定と返金は、モジュールと Stripe をつないだときに起きる。
- このリポジトリは公開されており、複数の開発者と CI が、同じ Stripe のアカウントのサンドボックスを使う。

## 検討した選択肢

### テストの道具

| 選択肢 | 判断 |
|---|---|
| **pgTAP(データベースの関数と、行ごとの決まり)、Vitest(Next.js のアプリの処理)、Playwright(画面の流れ)** | 採用。使う技術(TypeScript、Next.js、Supabase)で、広く使われている。pgTAP は、Supabase の手元の環境で動かせる |
| Deno のテスト | 採らない。Supabase の Edge Functions を使わないため、Deno で動くコードがない(ADR-0010) |

### 結合テストでの Stripe

| 選択肢 | 判断 |
|---|---|
| **Stripe のサンドボックスにつなぐ** | 採用。サイトの記録と Stripe の一致は、本物の Stripe の返事でしか確かめられない。方式検証でも、公式ページの記述と、サンドボックスの動きが違う点があった(ADR-0009) |
| Stripe を、すべてのテストで置き換える | 採らない。置き換えたものは、開発者が思う Stripe の動きであり、食い違いを見つけられない。単体テストでは、置き換える(速さと、サンドボックスで起こせない出来事を起こすため。TST-031) |

### 結合テストでの仮押さえ

| 選択肢 | 判断 |
|---|---|
| **Playwright で、アプリの購入手続きの画面から、テスト用のカードで払う** | 採用。Checkout Session の支払いは、サーバーからは送れない(Stripe の公式ページ「The Checkout Session object」)。本番と同じ道を通る |
| 支払いを、Checkout Session を通さずに、直接作る | 採らない。本番が通らない道であり、カードのブランドの確かめと、Checkout Session から読む値を、確かめられない |

### 結合テストでの Stripe の知らせ

| 選択肢 | 判断 |
|---|---|
| **テストが、署名を付けた知らせを、アプリの入口に送る** | 採用。知らせは合図として使い、中身は Stripe から読み直すため(IF-043)、読み直す中身は本物である。重なり、順の入れ替わり、届かないことを、毎回同じ形で起こせる。サンドボックスを共有しても、ほかの人のテストの知らせが届かない |
| Stripe の CLI で、Stripe が送る知らせを、手元と CI に届ける | 採らない。同じサンドボックスのすべての知らせが届き、ほかの人のテストの知らせで、テストが落ちる。届く順と時刻を、テストが決められない |
| 開発者ごとに、サンドボックスを持つ | 採れない。サンドボックスは、1つのアカウントで5つまでである(Stripe の公式ページ「Manage sandboxes」) |

### 期限の確かめ方

| 選択肢 | 判断 |
|---|---|
| **記録した日時を、過去の日時にして記録を作り、期限で動く処理の入口を呼ぶ** | 採用。期限で決まる扱いは、記録した日時から、そのつど求めるため、本番と同じコードが、本番と同じ道を通る |
| 今の時刻を、外から渡せる口を作る | 採らない。本番で誤って使われると、すべての仮押さえが、期限を過ぎたものとして取り消される |

## 決定

1. テストの段は、単体テスト(pgTAP、Vitest)、結合テスト(Vitest。仮押さえには Playwright)、E2E テスト(Playwright)の3つにする(TST-001〜TST-003)。
2. 単体テストも、データベースは、手元で動かす Supabase を使う。Stripe と、メールを送るサービスは、単体テストでは置き換え、結合テストでは、Stripe だけを、サンドボックスにつなぐ(TST-004、TST-013〜TST-017)。
3. 結合テストと E2E テストは、流れがつながった機能の PR で書く。コードを変える PR のたびに、単体テスト、結合テスト、E2E テストを自動で動かし、通らない PR は、マージできなくする。E2E テストのうち、Stripe が送る知らせで進む流れは、main にマージして、検証の環境に置かれるたびに、検証の環境でも動かす(TST-006、TST-008、TST-010)。
4. 結合テストの仮押さえは、Playwright で、アプリの購入手続きの画面から起こす。Stripe の知らせは、テストが署名を付けて送る。Stripe が実際に送る知らせの種類と順は、検証の環境の E2E テストで確かめる(TST-018〜TST-020)。
5. Stripe のサンドボックスは、開発、CI、検証の3つを持つ。CI に置く鍵は、このリポジトリのブランチからの PR にだけ渡す(TST-009、TST-022)。
6. 期限は、記録した日時を過去にして確かめ、今の時刻を外から変える口は、作らない。期限の境目は、単体テストで、時刻を決めて確かめる(TST-025〜TST-031)。
7. 必ず確かめる範囲は、すべての遷移と、重大な不具合の6つを軸に決める(TST-032〜TST-039)。ADR の、あとで確かめる項目は、いつ確かめるかに分ける(TST-040〜TST-044)。

## 影響とリスク

- 結合テストと E2E テストは、Stripe のサンドボックスを呼ぶため、単体テストより遅く、Stripe が止まっている間は、通らない。その間は、PR をマージできない。
- 仮押さえを使う結合テストは、ブラウザを通すため、1件ごとに時間がかかる。かかる時間は、測っていない。
- 支払いを受け付けられる生産者の Stripe のアカウントは、サンドボックスごとに、人が1回登録する(TST-024)。サンドボックスを作り直したときは、登録し直す。
- 開発者は、開発のサンドボックスを共有する。テストは、そのテストが作ったものだけを使う決まり(TST-023)で、ぶつからないようにする。
- 実装のテストで確かめること:
  - 自動のブラウザ操作で、生産者の登録(Stripe の埋め込みの部品)と、メールのリンクを開く操作を、通せるか。通せない操作は、テスト・品質確認の工程で、人が行う。
  - 生産者のアカウントの状態の知らせ(IF-053 の v2 の形)に、テストが署名を付けられるか。付けられないときは、その知らせだけ、検証の環境の E2E テストで確かめる。
  - サンドボックスで、返金が失敗に変わることと、仮押さえの失効を、起こせるか。起こせないものは、単体テストで、置き換えた Stripe で起こす(TST-031)。
  - 仮押さえを使う結合テストに、かかる時間。
  - CI で動かすアプリで、Vercel の BotID(AUTH-042)が、開発のときと同じく、すべての求めを通すか。通さないときは、CI の E2E テストにも、検証の環境と同じ、テストの求めを通す設定を使う。
